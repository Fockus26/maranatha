# D082 · Backend · De Supabase al Postgres del VPS: Drizzle + Better Auth + Brevo, comprobantes en la base, corte junto al paso a Docker · Implementado (pendiente de corte)

**Decisión:** la base, el auth y el Storage salen de Supabase. Datos con **Drizzle** sobre el Postgres central del VPS (`kit-db`: `maranatha` producción, `maranatha_preview` para Vercel, `maranatha_dev` para desarrollo; QA en Docker). Sesiones del dashboard con **Better Auth** dentro de la app (sin registro, acceso por `ADMIN_EMAILS` como antes). **Recuperación de contraseña** nueva, por correo vía **Brevo SMTP**. Los **comprobantes** pasan del bucket `receipts` a la tabla `payment_receipts` (`bytea`). El **corte coincide con mover producción a Docker en el VPS** (rama `vps`); Vercel queda solo de pruebas contra `maranatha_preview`.

**Por qué:** César pidió el corte directo al VPS. Comprobantes en la base porque el VPS ya respalda cada base a Backblaze cada noche (`kit-db backup --all`) y César no quiere un bucket propio del proyecto; además sirve igual desde Vercel (sin disco persistente) y desde Docker. Volumen esperado: decenas de comprobantes de ≤4 MB al mes, muy por debajo de lo que molesta a Postgres.

**Detalle:**
- **Esquema:** `lib/db/schema.ts` reproduce las migraciones de `supabase/migrations/` (checks, índice único parcial por `reference_norm`, columna generada) sin RLS, grants ni `storage.*`. Funciones (`hit_rate_limit`, `payment_month_stats`, `set_updated_at`), triggers y la vista `project_raised` en `drizzle/0001_*` a mano. `auth_email_exists` desaparece: el login consulta `"user"`.
- **Autorización:** no había políticas RLS (todas las tablas tenían RLS sin políticas, acceso solo por el servidor con la clave secreta), así que no hay reglas que portar: la única puerta sigue siendo `getAdmin`/`getAdminStrict` en páginas, Server Actions y la ruta `/dashboard/comprobantes/[id]`.
- **Auth:** ids uuid conservados; el hash bcrypt de Supabase se verifica con `bcryptjs` y el resto con el scrypt de Better Auth (cada admin pasa a scrypt al cambiar su contraseña). `requireEmailVerification` como Supabase. La ruta `/api/auth/*` solo expone `GET /reset-password/<token>`; login, salida y contraseña nueva van por Server Actions. Límite por IP (10/15 min) y por cuenta (5 fallos/15 min). Todas las sesiones se pierden en el corte: cada admin vuelve a ingresar una vez.
- **Correo:** `lib/email/send.ts` (nodemailer + React Email), `SMTP_*` en Vercel y en el VPS, Mailpit en QA. Solo se envía a correos de `ADMIN_EMAILS`; la respuesta del formulario es la misma exista o no la cuenta.
- **Importación:** `scripts/migrate-from-supabase.ts`, una transacción, compara md5 del contenido por tabla y de los bytes de cada comprobante; `--dry-run` es el ensayo.
- **Rollback:** el proyecto de Supabase queda **vivo y sin escrituras 30 días** (hasta ~30 días después del corte). Volver = re-desplegar el commit anterior al merge (`deploy/README.md` › Operación) con las variables de Supabase; los datos escritos en el VPS después del corte se re-copian a mano. Borrar el proyecto es acción de César, comparando los datos antes.
- **Descartado:** Cloudflare R2 (otro servicio y otra clave sin necesidad), disco del VPS (no sirve desde Vercel y sale del respaldo de la base), dejar Storage en Supabase (el proyecto no se podría apagar).

**Nota de estado:** Implementado en `feat/migrate-vps` (PR en borrador hasta el corte).
